## Questions for the Engineer (via the tech lead)

**1. Should Zurfur refuse a DID document whose PDS address is more than a bare origin (a path, a query or a fragment)?**
- The DID spec says the address "should contain only the URI scheme …, hostname, and optional port number" (atproto.com/specs/did, fetched 2026-10-08).
- Bluesky's reference code accepts any URL that parses, and jacquard deliberately keeps a path prefix.
- There is no security effect either way: only the document's own controller is affected, on a host they already control.
- **(a)** Refuse. This follows the spec's wording, as port 443 only (Q1) already does. A non-conforming PDS can't sign in or show a profile.
- **(b)** Accept, as now. The `blob_url` fix lands either way.
- **Recommendation: (a).** The lockout is narrow and matches the strict posture you chose for Q1 and for handles. It also lets every later caller treat the PDS as an origin.

**2. Should the sign-in cookie be cleared on every callback, or only when it matched that sign-in?**
- Today every callback clears it. So a page open in the visitor's browser can cancel their sign-in in progress, and with two tabs both sign-ins can fail. The visitor retries either way, and login-CSRF protection is unaffected.
- **(a)** Keep clearing on every callback. Simplest.
- **(b)** Clear only when the cookie matched this sign-in. Otherwise it expires within 10 minutes or the next sign-in replaces it. This needs one new error name in the sign-in port.
- **Recommendation: (b).** It closes both cases, and the cookie left behind is harmless: it binds one single-use sign-in, and the server enforces the 10 minutes. This can follow the merge.

**#240, `authenticator.rs:215`**
> Claude: Agreed for this slice as it stands. The race you describe, where the loser finds the request already gone, is fixed up the stack in #242: jacquard's `MissingState` now means "another attempt owns it", and nothing is deleted. A wider variant remains: both attempts read the request before either deletes it, and the losing code exchange fails with an ordinary error. jacquard saves a session only after a successful exchange, so in #242 we'll delete only when this attempt may have saved one: its own save failed, it signed in as the wrong account, or the deadline cut it off mid-save. Since #242, this race also needs the same browser twice.

**#240, `delete_sessions_by_id.sql:4`**
> Claude: Agreed. On Postgres 16, a filter on the trailing primary-key column scans the whole index, and nothing else deletes these rows, so the table only grows. We'll add an index on `session_id` with `just migrate-add`, as we did for `account_members`.

**#241, `profile.rs:58`**
> Claude: Partly agreed. The XRPC request is fine: jacquard builds it from the scheme, host and path only, so a query or fragment never reaches it. `blob_url` is what goes wrong, because it pastes the whole string. We'll build it the way jacquard does, which also encodes the CID, and test all three shapes. Only the document's own controller can cause this, on a host they already control. Whether to refuse such documents outright, as the DID spec's "should" suggests, changes who can sign in, so we've asked the Engineer.

**#242, `api-proxy.ts:26`**
