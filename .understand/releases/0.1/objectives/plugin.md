# 0.1 objectives: plugin

Stage: pre-alpha-v0.1.0 · Lead: Octopus · QA: Mantis

**No 0.1 work for the plugin team.** The Delivery Plan gives us no work package, and no plugin code exists: the code mentions plugins only in comments and in tests that pin that `golem` is not an actor kind (a Golem is a User). Project MVP puts the plugin surface, Golems and Portals in the beta, and plugin credentials and the marketplace in Release. Our people are free if the tech lead wants to lend them (a second security reviewer for the arms is the tech lead's call, Delivery Plan, risk register). One thing 0.1 needs from us anyway:

## Objectives
1. **den.proto stays open for plugins, and 0.1 proves it.** den.proto's spellings freeze when the alpha ships, and plugins arrive in the beta, so whatever they need must be addable without a break. Three openings do that:
   - an unknown `type` gets a generic icon, so a plugin's own type can travel later;
   - an unknown content case shows "content not shown yet", so content a plugin renders can arrive as a new case;
   - the two requests carry only the path, `includeDeleted` and `pageToken`: no viewer, no root, no "on behalf of", so a Golem could later read as itself, on its own credential.

   Done when: (a) the committed `contract/zurfur/api/v1/den.proto` (after the den.proto package) still says all three in its comments, and its two request messages hold only those fields; (b) the web's tolerant-reader tests decode a node of an unknown type and an open node with an unknown content case, and pass in `just gate`. Today the draft (revision 2.1) says all three; the tests don't exist yet, and the TDD's tolerant-reader list names an unknown kind, not an unknown type. Serves: the den.proto contract (your review, D-6), the den.proto package, and the web's wiring to den.proto.

## Where the stages change our plan
- **No build work before the beta.** One review duty may come before the alpha: the type catalog's rule for plugin types, if that decision lands first (question below).
- **den.proto's doors close at the alpha, not at 0.1.** In pre-alpha it may break and stay tagged `v1`, so a seam missed now is still fixable. We check now because you review den.proto now, and a fix costs least before your approval.
- **No plugin rigor on the host seam.** Atta's host trait and Zurfur's type enum are internal Rust, changeable at any stage; plugin types later add one enum variant (the My Den rulings' recorded direction). Seat ceilings are commission's alpha work, and how they fit the Den is still open. 0.1 gives a Participant standing over the whole commission, which matches the default ceiling (Total), so 0.1 closes nothing there.
- **What stays strict:** signing in as a chosen user stays dev-only. The dev profile's fixed sign-in and its switch, and the web's mock sign-in, keep their guards and reviews; pre-alpha relaxes none of them. We add no check of our own.

## Not this release
- **All plugin work:** Golems, Portals, the plugin API, scopes, keys and listings, placed in the beta or Release. Nothing to cut from 0.1, and nothing missing.
- **The publisher-ban kill switch.** We back recommendation B (it ships with plugins) of "Q8. Kill switches for beta features" in `.understand/20261008-moderation-study.md`, which you haven't answered yet. Our proposed check points went to the moderation lead on the board.
- **The Den on a second surface.** Auth Surfaces' threat pass requires that out of scope look like nonexistent. The Den already has no lookup by DID (every path starts at the viewer's own root), and the den lead's hiding method (D-15) is where a plugin's scope could refuse a node as the one not-found; we back it. Equal timing and per-key rate limits come with that surface.
- **Beta notes:** the versioning rules' tolerant-reader clause names `/api/{major}/*` only, so it must name the plugin surface if den.proto's messages are served there; a test header in `commission_seat_invitations.rs` says a Golem can't be invited, which changes once Golems are Users.

## Questions for the Engineer (each pre-answered)
- **How does a plugin's type show on the wire?** Not needed for 0.1; flagged early because the type catalog is a one-way door. (a) A reserved name shape, such as a prefix, carrying the plugin's own type name. (b) One `type` value for every plugin node, as the changelog gives every plugin entry one kind, with the plugin's own type name in a field only openers see. A card shows `type`, so under (a) every card viewer learns which plugin made the file. *Proposed answer: (b),* decided with the type catalog. It keeps a plugin from passing for a core type, and a card says only "a plugin's file". Either stays addable after the alpha as long as no core type takes the reserved value or shape, and none does today.
