## Objectives
1. **The frame and My Den on mock data are merged and clickable.** Done when, on `main` (on the shell's branch if question 1 is no):
   - `just dev-mock`, sign in, "Open My Den". The tree works with the keyboard (Tab in, arrows, a letter jumps). Founding an Account on `/accounts` makes it appear under `accounts` in the tree. At 320 px, ☰ opens the drawer.
   - `just dev`, signed in with your handle: the Accounts pages work inside the frame; there is no sidebar, tree or "My Den" link; a typed `/den` shows "Nothing here". Stop the API, click "Sign out": DevTools → Application → Cookies shows no `zurfur.sid`.
   Serves: the Explorer frame, and My Den on mock data (milestones "today's Accounts pages in the dark frame" and "browse alice's mock Den").
2. **den.proto reaches the contract as you approved it.** Done when: the Technical Design Document's den.proto decisions (the draft as a whole, the query-parameter spelling, what a card carries, DIDs and the id rule, an archived card, the soft-deleted word's field name) carry your answers; the contract PR's CI `contract` job is green; and `den_pb.ts` sits in `frontend/web/src/lib/server/api/generated/zurfur/api/v1/`. Serves: the den.proto revision (written), and den.proto into the contract, with the den team. Timing: question 2.
3. **My Den shows the real backend through the same screens.** Done when: start the dev-profile recipe (the dev-profile package names it), sign in as alice, and open My Den. You see "Supreme Arts", Ember, Kael-sona and "Untitled" with its four entries, and `/den/nope` shows "Nothing here". As bob (if the switch survives the cuts), you see Abco and "Untitled" and no Account. The `just gate` output lists the web's golden-response spec passing, one test per golden response the den team commits. On `just dev` the Den stays hidden. Serves: the web's wiring to den.proto, and the live run.
4. **Nothing leaks from the web, on mock and live alike.** Done when, on the dev profile: DevTools → Network shows every request going to Zurfur's own address (on `just dev`, your own avatar is the one exception). DevTools → Application shows no local storage, session storage or IndexedDB for the site, and `zurfur.sid` is the only cookie. A Den page's response headers carry `cache-control: private, no-store`, `referrer-policy: same-origin` and `content-security-policy: frame-ancestors 'none'`. Every Den page's tab title reads "My Den · Zurfur". The web's terminal log never shows a DID, a Den path or a page token. The end-of-slice security review lists no open must-fix for the web. Serves: "Nothing leaks" (My Den's privacy rules) and the end-of-slice security review.
5. **The frame's accessibility is checked, and stays checked.** Done when: `.understand/releases/0.1/checks/web-accessibility.md`, recorded by Crow, holds a keyboard-only walk of My Den on a desktop and the 320 px run. And the web suite holds a contrast test, built in the live run, that turns `just gate` red when a declared colour pair drops below WCAG 2.2 AA. The pairs are each text, icon, control-edge and focus colour on the backgrounds it sits on. The thresholds are 4.5:1 for text, and 3:1 for large text and for non-text (success criteria 1.4.3 and 1.4.11, as Crow fetched them on 2026-10-09). Serves: the keyboard, phone, screen-reader and dark-style stories (success criterion 6).

## Where the stages change our plan
- **den.proto may stay changeable through 0.1, if the tag allows it.** The plan holds Phase 2 behind your den.proto review because its spellings "can't change once the alpha ships". Pre-alpha lets the proto break without leaving `v1`. But the contract's lifecycle file ends its pre-release period "when the first release tag is cut", and from then on CI also checks breaking changes against that tag. So whether `pre-alpha-v0.1.0` closes the door is yours to say (question 2). Until you answer, the review keeps blocking.
- **The shell could reach `main` before the backend** (question 1). Since slice 1b, the everyday stack shows no Den (tested). Mock mode runs only in a dev build: a production server started with the mock flag refuses to boot.
- **Token names stay cheap to rename** through 0.1: no theme file uses them yet.
- **Rigor that stays, whatever the stage:**
  - Den links: one path builder; a link is parsed back before it's trusted; lint stops any other code from minting one.
  - Answers: the one not-found; a decoder that fails closed (an unknown access shows as a card, an unknown level never as Public).
  - Headers and logs: `no-store`, `same-origin` and the framing refusal; logs carry route names only.
  - The browser: nothing in its storage; tree memory tied to the signed-in user, with a full page load on every change of user; generic page titles.
  - Sessions: the sign-in gate on every signed-in route, with its one sign-out exception; mock mode's boot guard.
  - **Added in the wiring:** a cap on the parallel reads of the folders above an item (Heron's note: a deep page makes up to 17 reads at once), and a dev-profile flag that is off in any production build, as mock mode's is.
  - **One I'd add to the plan:** Heron reviews the wiring. Its decoder and that flag are privacy guards, and the plan gives the wiring QA only. That's the tech lead's call.
- **Rigor pre-alpha doesn't need:** measuring by hand placeholder colours that Claude Design will replace. The contrast test does it on every gate (question 4).

## Not this release
- **Nothing to cut from the web's list:** steps 1 and 2 are built, and the wiring and the live run are small.
- **Held in reserve:** moving the golden-response tests from the wiring into the live run would shorten the critical path by one unit. The plan leaves that to me, but it is also the plan's fallback if Atta's read side runs long, so I'm keeping it for that.
- **Missing from the plan:**
  - The web half of the dev-profile flag. The design gives it to the web builder, but no work package names it. It goes in the wiring.
  - Who builds the dev-only "sign in as" page. That's open, for the tech lead.
  - The shell's branch, which the merge plan never mentions (question 1).
- **Left out on purpose:** a light-theme switch (it needs your preferences file); the dotfiles toggle (no dotfile exists); loading other people's avatars through Zurfur (it comes with the User Page).
- **You'll meet this in the live run:** if the API isn't running, the sign-in gate treats you as signed out. It isn't new, and fixing it isn't 0.1 work.
- **Planned ahead: loading states** (the Engineer, 2026-10-09: "so that people don't just LEAVE if nothing loads"). Not a 0.1 objective; where it lands is yours.
  - **What shows, by time** (one rule for the tree, the pane, a card and the path bar):
    - under 300 ms, nothing changes, so a fast read never flashes;
    - from 300 ms (the pane's delay today; the tree, which shows its skeleton at once, adopts it), Skeleton rows where the content will go, with the container marked busy;
    - from 3 s, a calm line under them, "Still loading…", announced politely;
    - at the time limit, "Zurfur isn't answering right now." with "Try again". Never "Nothing here", an empty folder or the sign-in page.
  - **Full page loads are the gap.** The server renders the page, so the browser shows nothing until the backend answers, and only a time limit bounds the wait. Streaming the Den read would let the frame paint first, with a skeleton. But streaming needs the page's script, and a streamed read can't redirect or change its status, so the sign-in check stays ahead of it (svelte.dev, "Loading data", read 2026-10-09).
  - **Time limits, for Heron's note** (the gate's backend calls have none, so a hung backend makes signed-in pages wait).
    - *Proposed:* every web-server call to the API gets an abort signal, as sign-out's 5 s already does: **5 s for the session check (`/me`)**, which every signed-in page waits on, **10 s for every other call**, and **15 s for the whole request**, so hanging folder reads can't hold a page for 50 s.
    - A call that runs out fails as a network failure. The gate answers it itself, with its own fixed "isn't answering" page carrying the usual headers: never "signed out", and never the frame, where a form action would run with no session. A folder read that fails shows "Couldn't load. Retry." in the tree instead of vanishing. The limits and the gate's page ship in one slice; alone, the limits would send a slow `/me` to the sign-in page.
    - It's small (S), and it can ride the wiring if the tech lead wants it in 0.1.
  - **Kept compatible in 0.1:**
    - each Skeleton row takes the height of the row it stands in for (`--row-height`; today it uses `--space-3`, a small shift to fix);
    - the pane's header keeps its height while loading, and the avatar has a fixed size;
    - no layout waits on content to find its size.
  - **For the Claude Design brief:**
    - Skeleton variants (a tree row, a pane row, a card, a header line), and a quiet progress bar for navigations;
    - InlineMessage's "still loading" (info) and "isn't answering" (error, with Retry);
    - tokens: `--color-skeleton` (new; Skeleton uses `--color-surface-raised` today), `--duration-skeleton` (app-owned today), `--delay-busy` (300 ms) and `--delay-slow` (3 s). Reduced motion stops the pulse, as it does today.
  - **QA (Crow, 2026-10-09):** the facts hold: sign-out's 5 s bound, no bound on `/me` or any other call, `--row-height`, the fixed-size avatar, reduced motion stopping the pulse, and svelte.dev's streaming limits. No time limit leaks anything or opens anything: a timed-out Den read still fails to the error page, never "Nothing here" (`den.ts`, `readOutcome`; `runtime.ts`), and a bounce to sign-in keeps the cookie. 1 should-fix, 2 notes, no must-fix.
    - *should-fix:* **the gate must answer a timeout itself, in the same slice as the time limits.** A throw from the `handle` hook gets SvelteKit's bare fallback page (the app has no `src/error.html`), and that page carries none of the framing, `no-store` or referrer headers, because the outer hooks stamp only what `resolve` returns (kit `utils.js`, `handle_fatal_error`; `handle-chain.ts`). Resolving on to the frame's error view would let a form action run with no session behind it, since actions run before layout loads (Heron's round 2, row 9). So the gate should return its own fixed "isn't answering" page. Shipped alone, the time limits would turn every `/me` slower than 5 s into the sign-in page this entry rules out, because the gate reads a network failure as signed out (`session-gate.ts`, `sessionOrAnonymous`).
    - *note:* the limit is per call, not per page. Under the wiring's cap of 4 reads in flight, a node that answers while the 16 folders above it hang holds a full page load for about 50 s. Those folder reads also drop any failure silently, so the tree opens less far and nothing says "isn't answering" (`den.ts`, `readAncestors`, `catchAll`). A deadline for the whole request would bound both.
    - *note:* the pane waits 300 ms before showing it is busy (`BUSY_DELAY_MS`), not 200, and the tree shows its skeleton at once (`TreeBranch.svelte`). `--color-skeleton` would be new: Skeleton uses `--color-surface-raised`. A streamed Den read can't do the load's two redirects (a stale page token, an ended session), so the page itself would have to show those.
  - **Resolved (Fennec, 2026-10-09):** all three, in the lines above. The gate answers a timeout with its own page, in the same slice as the limits. A 15 s deadline covers the whole request, and failed folder reads show a retry row. The delay is 300 ms, and `--color-skeleton` is marked new.
