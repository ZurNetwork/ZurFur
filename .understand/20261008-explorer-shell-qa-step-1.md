**What Finch did differently, checked:**
- **The sign-in gate now lives in the server hook.** It works: a stale session gets a 303 to `/login`, and a data request gets SvelteKit's JSON redirect. Every `(session)` load, data request and form action is gated before it runs (planted: gate removed; 4 tests went red). Two things to know, neither a regression:
  - **For Heron:** a redirect the gate throws skips every outer hook, so it leaves without `Cache-Control`, `Referrer-Policy` or the frame headers. That's because SvelteKit builds a thrown redirect's response outside the `handle` chain (`runtime/server/respond.js`, the `catch` around `handle()`). In practice this does no harm. A 303 isn't among the statuses HTTP lets a cache store without explicit freshness (RFC 9110 §15.1), and its next hop, `/login`, is on the same origin. `src/NODE.json` documents this exception for the frame headers, but its no-store line still says "every response to a signed-in request" is stamped, and the gate's redirect isn't. Proof: a stale cookie on `/accounts` returns 303 with only `location: /login`. Fix: name the same exception on the no-store line.
  - **Sign out during a backend outage looks like it worked.** With the backend unreachable, "Sign out" lands on "Sign in", and no cookie is cleared. That's because the whoami fails, the gate takes it for signed out, and the action never runs. When the backend returns, the same browser is signed in again. This isn't new: the same POST at the old step 1 (9dba2fcf) also returned 303 to `/login`, through the layout gate. The design already flags "a stopped backend looks like being signed out" as a separate call. It's raised under Q2 in the steps 1b–2 file.
- **The skip-link test** reads the order of the focusable elements, checks the skip link is first, then focuses it and presses Enter, and expects the main pane to have focus.
