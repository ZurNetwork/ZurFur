# Hardened resolver: QA of slices 1 and 2

2026-10-08 · Magpie (identity QA) · Reviewed: slice 1 "the domain words" (Lynx, change `rukvlkst`, commit `44de1da793ab`) and slice 2 "the guarded web client" (Otter, change `vvltkpum`, commit `106b15ee938e`), against `.understand/20261008-hardened-resolver-design.md`. Security attacks are Heron's; this covers design fidelity, test quality and conventions.

## Summary

**Slice 1, the domain words (Lynx): 1 must-fix.**
1. **The shared test suite misses two promises the port makes.** The real resolver in slice 3 must pass this suite, so a gap here is a gap there too. Two deliberate bugs in the in-memory fake went unnoticed:
   - asking for the handle of a DID whose own document is refused quietly answers "no handle", when the design says it must be an error;
   - a DID whose claimed handle points nowhere answers with an error, when it must be "no handle".

   Fix: stage those two cases in the suite.

Everything else in slice 1 matches the design. The new handle type follows every rule in the design, and the old handle type's tests and doc examples pass unchanged.

**Slice 2, the guarded web client (Otter): 2 must-fix.**
1. **Certificate failures get the wrong label.** A failed TLS handshake (a bad certificate goes the same way) comes back as "unavailable, try again". The design says it is "refused". Meanwhile a host that sends a garbled body gets labelled a TLS failure. I measured both. The test for this builds its own error chain, which doesn't match the one reqwest really produces, so it passes anyway.
   - Why it matters once slice 3 lands: a user whose handle's host has a bad certificate would get an error on every profile read, instead of falling back to their DID, and the planned first-seen job would retry them forever.
2. **The guard misses two of jacquard's ready-made clients.** `MemoryCredentialSession` and `UnauthenticatedSession` each build a bare reqwest client, and the second also uses Google DNS and the Bluesky fallback. Neither is on the forbidden list. The list Otter built is exactly the design's list, so the gap is in the design. The design's own rule is that the guard shuts "jacquard's convenience clients".

Everything else in slice 2 matches the design. All 30 deliberate bugs I planted in the address table, URL policy, DNS filter, redirects, body cap and guard were caught, apart from the four listed under "Mutations" below. `cargo deny` passes.

**Question for the Engineer (one):**
- **Should the new handle type remove spaces around a handle, or refuse them?**
  - The atproto handle spec says a handle has no whitespace, "including as prefix/suffix".
  - The design you approved says the type trims them, and Lynx built that. Lynx raised the conflict.
  - The web form already trims before it sends, so sign-in through the site works either way.
  - It matters in slice 3. The same parser will read handles out of DID documents, where the DID spec says to take the first *valid* entry. With trimming, a space-padded entry counts as valid, so Zurfur could pick a different handle than Bluesky would. The both-ways check still stops impersonation.
  - **(a)** Keep trimming in the type, as built.
  - **(b)** Make the type strict, and trim only where people type: the sign-in route and the CLI.
  - **Recommendation: (b).** The type then means exactly "a handle by the spec", and documents get no special case. Today's `trim` also strips non-ASCII spaces (U+00A0, U+3000), while lowercasing is ASCII-only. Under (b) that mismatch goes away too.

**For the tech lead (no decision needed from the Engineer):**
- Three hand-kept copies of the same top-level-domain list now exist: two in `domain` and one in `adapter-atproto`'s URL policy.
- The design doc's security check 2 says to diff the address table in `policy.rs`; it now lives in `address.rs`.
- Heads-up for slices 3 and 4: rustls's certificate-name error text includes the hostname. So the info-level logs must log only the failure class, never `{:#}` or `{:?}` of the cause.
- Slice 2's `NODE.json` note points at this `.understand/` design. Repoint it when the design is recorded as a DD.
- Slice 2 also edits `deny.toml`, which isn't in its planned file list. It's correct, and it records your hickory ruling.

## Conventions and scope

- **Tests beside their leaf, no inline `mod tests`, no `mod.rs`:** clean in both slices. `scripted.rs` is a `#[cfg(test)]` leaf in `src`, as it must be, since `AddressLookup` is crate-private.
- **Path-qualified derives, `thiserror` on errors, no `Deref`:** clean in both.
- **Doc comments 1–4 lines, no DD numbers, page ids, Jira keys or PR numbers:** clean. The scan of added lines found pointers only in `NODE.json` and in a `deny.toml` comment.
- **Inherent constructors justified (rulebook ruling 6):** `GuardedHttp::new`, `SystemDns::from_system_conf` and `FilteringDns::new` each carry the one-line reason. `V4Block::new`/`V6Block::new` are private `const fn`s for a `const` table; a one-word "const" note would complete them (nit).
- **Named `let`s, `ok_or`/`let-else`/`map_err`:** followed. One-line expected values stay inline, which is consistent with ruling 3's "multi-line"; §5's stricter "each expected value" wording isn't applied to one-liners (nit, no action).
- **Scope:** nothing from slices 3–6 leaked in: no `resolver/`, no `JacquardBridge`, no authenticator port change. Files match §4, plus these justified extras:
  - slice 1: `adapter-mem/tests/identity_resolver.rs` (the runner), the `mod`/`pub mod` lines, four `NODE.json`;
  - slice 2: `deny.toml`.
- **Leaf name (observation):** `handle/at_handle.rs` isn't in ruling 10's fixed leaf vocabulary (`values.rs` would be), but design §3.1 named the file, and `handle/domain.rs` is precedent. No action unless the tech lead wants it.
